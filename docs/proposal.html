Tabstage

Una app de escritorio para macOS y Linux donde organizas tus tabs en grupos y carpetas, y cada grupo decide en qué navegador se abren. Sin extensiones y sin permisos especiales en el navegador.

Así se vería

El diseño continúa el de la extensión: la misma paleta Catppuccin (Latte en claro, Mocha en oscuro), IBM Plex Sans para el texto y Plex Sans Condensed para títulos, cuadros de estado de 9 px y radios de 6–10 px. Es una herramienta que se usa decenas de veces al día, así que la prioridad es leer rápido y abrir con un clic. Los mockups siguen el tema de tu sistema.

Qué pasa al hacer clic en un tab

  1. Se toma el navegador del grupo: el que tenga asignado o, si no tiene, el navegador por defecto. Si el asignado ya no está instalado, se usa el por defecto y se muestra un aviso en el grupo.
  2. Si ese navegador permite consultar sus tabs, se busca uno con la misma URL (sin #fragmento ni barra final).
  3. Si lo encuentra, trae esa ventana al frente y activa el tab. Si no, abre la URL en un tab nuevo de ese navegador.

En macOS, la primera vez que la app consulta los tabs de un navegador, el sistema pide permiso de Automatización. Si tu Mac es administrado (MDM) y ese permiso está bloqueado, la app lo detecta y abre el tab en uno nuevo, sin errores.

Por qué Tauri 2 y no Rust puro

Con Tauri 2, todo lo que importa vive en Rust: el modelo de datos, la persistencia, la detección de navegadores y la apertura de tabs. La interfaz se hace en React + TypeScript, que es lo que más usas. Es la forma más común hoy de hacer apps de escritorio con Rust.

Arquitectura

Es un workspace de Cargo con la lógica separada de la interfaz. El dominio no hace IO, así que se prueba con tests rápidos y deterministas. Todo lo que habla con el sistema (archivos, navegadores) se define con traits, y los tests usan dobles de esos traits.

# tabstage/
Cargo.toml            # workspace, lints y deps compartidas
crates/
  core/               # dominio puro, sin IO
    src/ids.rs        # GroupId, TabId, FolderId, BrowserId
    src/workspace.rs  # Workspace, Group, Node, Status
    src/commands.rs   # add/move/reorder/rename… → Result
    src/browser.rs    # BrowserChoice, effective_browser()
    src/url.rs        # TabUrl (validada) + normalización
  store/              # JSON atómico, migraciones, watcher
  browsers/           # traits + impl macOS / Linux
    src/macos/        # LaunchServices, open -b, AppleScript
    src/linux/        # .desktop XDG, xdg-settings, Exec
src-tauri/            # capa fina: comandos IPC, bandeja, atajos
ui/                   # React 19 + Vite + TypeScript
  src/bindings.ts     # generado por tauri-specta
.github/workflows/    # ci.yml, release.yml, pages.yml
site/                 # GitHub Pages + install.sh
pub enum BrowserChoice {
    Default,
    Specific(BrowserId),
}

pub struct Group {
    id: GroupId,
    name: String,
    color: AccentColor,
    browser: BrowserChoice,
    children: Vec<Node>,
}

pub enum Node {
    Tab(Tab),       // url, title, status
    Folder(Folder), // name, status, tabs
}

/// Navegador con el que se abre un grupo.
pub fn effective_browser<'a>(
    group: &'a Group,
    settings: &'a Settings,
    installed: &BrowserSet,
) -> Resolved<'a>

Reglas de código (rust-skills)

  • Errores con thiserror en los crates y anyhow solo en src-tauri. Sin unwrap() fuera de los tests; lo vigila clippy.
  • Newtypes para los IDs y para la URL validada: se valida al entrar y el resto del código recibe datos que ya son correctos.
  • Enums en vez de strings para el navegador elegido, los colores y los estados de foco.
  • Serde con versión de esquema, #[serde(default)] para compatibilidad y migraciones con tests de snapshot.
  • Lints a nivel de workspace (clippy::pedantic selectivo), rustfmt en CI, rust-version declarado, tracing para logs y perfil release con LTO.

Desarrollo con TDD

Cada cambio empieza con un test que falla, luego el código mínimo que lo hace pasar y después el refactor. Se construye de adentro hacia afuera para que cada capa nueva se apoye en una que ya está probada.

  1. core: invariantes del modelo (orden sin huecos, carpetas sin anidar, estados válidos), comandos y effective_browser. Proptest para las operaciones de mover y reordenar.
  2. store: ida y vuelta JSON con snapshots de insta, migración v1→v2, escritura atómica y recarga ante cambios externos.
  3. browsers: la lógica (normalizar la URL, buscar el tab, decidir entre enfocar o abrir) se prueba con mocks. Los adaptadores reales se cubren con tests de integración marcados #[ignore] que se corren a mano.
  4. src-tauri: comandos IPC probados contra el estado con dobles.
  5. ui: componentes con Testing Library e IPC simulado. Los flujos E2E corren en Linux en CI.

Cómo se comparte

Lo más común para apps de Tauri open source es combinar tres canales: GitHub Releases como fuente única de los binarios, una página en GitHub Pages con un script de instalación y un tap de Homebrew. Compartir solo el repo obligaría a cada persona a instalar Rust y Node para compilar, así que no basta.

Instalación en una línea

curl -fsSL https://<usuario>.github.io/tabstage/install.sh | sh

En macOS copia la app a /Applications. Como el archivo llega por curl, no lleva el atributo de cuarentena y Gatekeeper no la bloquea aunque la app no esté notarizada. En Linux instala el AppImage en ~/.local/bin con su .desktop e icono, o usa .deb/.rpm si se pasa --system. El script verifica el SHA-256 publicado en el release.

Flujo de release

  1. Commits con Conventional Commits (como en la extensión).
  2. release-please abre un PR con la versión nueva y el CHANGELOG.
  3. Al fusionarlo se crea el tag y tauri-action compila en macOS y Ubuntu, firma la actualización y publica el release.
  4. Un workflow actualiza el cask del tap y la página de Pages.

Notarizar con Apple cuesta 99 USD al año y quita las advertencias en todos los canales. No hace falta para empezar: con el script de instalación es suficiente.
